Unresolved Questions for P3

Q1: Should candidate_skill_states have ON DELETE CASCADE for skill_id? Currently FK to skills(id) with no ON DELETE action (defaults to RESTRICT). If a skill is ever deleted, rows referencing it would block deletion. Unlikely for curated skills, but P3 should confirm.
Q2: Does P3 need UPDATE policy on interview_turns? Currently only SELECT and INSERT. The backend doesn't appear to PATCH turns, but if follow-up metadata needs updating post-creation, an UPDATE policy would be needed.
Q3: Should interview_reports.overall_summary allow NULL? Currently NOT NULL. The P3 backend defaults to report_data.get('overall_summary', '') — an empty string satisfies NOT NULL, but if the AI service omits it entirely and the fallback is changed, it could fail.
Note: question_bank.role and question_bank.round columns are nullable P3 filters on these only when the interview itself has them set. The seed data (008) leaves them NULL since the seeded questions are general-purpose. Company-specific filtering will work once production data populates these columns.

Bugs Found & Fixed During Validation

Fixed: Invalid UUID formats in migration 008 Original seed UUIDs had wrong segment lengths (e.g., 10-char first segments like faaaaaaaaa-…). Replaced all with valid 8-4-4-4-12 format UUIDs using distinct prefixes per entity type (a1=skills, b1=questions, c1=rubrics, d1=criteria).
Fixed: Missing INSERT RLS policy for interview_turns P3 backend creates turns via supabase.post('interview_turns', payload) using user-token, not service-role. Without an INSERT policy, this call would be rejected by RLS. Added ownership-chain policy.
Fixed: Redundant CREATE OR REPLACE FUNCTION handle_updated_at() Migration 007 originally redefined the trigger function already created in 004. Removed the duplicate; 007 now only creates the trigger referencing the existing function.
Fixed: UUID collision with recruiter seeds Skills originally used UUID prefix 22222222-…, which matched the Infosys recruiter UUID in migration 005. Different tables (no FK conflict), but confusing. Changed to distinct a1000000-… series.
